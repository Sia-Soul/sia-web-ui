# Windows 窗口未响应诊断

## 关闭加载中的网页时未响应（2026-10-27）

### 关闭后切离窗口的可恢复挂起

同日的安装版在 Ctrl+W 关闭页签并切到其他窗口后再次无响应，随后自行恢复。隔离测试复现了先关闭加载中的页签、创建另一个隔离网页、最小化并恢复窗口时的超时：Windows 等待链显示宿主主线程等待 `msedgewebview2.exe`，目标线程位于 `OneAuthUninitialize` 的退出清理等待中。主线程采样位于 `GetMessageW`，与下述 WebContext 互斥锁死锁不同。微软问题记录 [WebView2Feedback #5688](https://github.com/MicrosoftEdge/WebView2Feedback/issues/5688) 描述了相同退出栈和残留输入窗口导致宿主阻塞的路径；本机没有修改网络、系统服务或账号配置，也没有确认该记录中的网络触发条件。

仅调整网页焦点不能消除隔离测试的超时。早期临时方案为每个隔离空间保留 `HWND_MESSAGE` 空白控制器，避免触发内核退出；但资源回归发现关闭所有测试页签后仍留下多个约 110～130 MB 工作集的内核进程，因此已取消永久保活。

当前仅在隔离空间最后一个实际视图关闭时执行以下步骤：

1. 获取该 WebView2 内核的固定进程句柄，避免 PID 重用。枚举该内核的顶层 `IME` / `MSCTFIME UI` 输入窗口，只解除其中由本应用拥有的窗口的 owner；不改变子窗口、其他进程或仍有同组网页时的输入关系。
2. 在 UI 线程调用控制器的正常 `Close`，随后由 Tauri 移除外层窗口及注册记录。不保留空白控制器，也不删除隔离目录。
3. 后台给予内核 30 秒的退出清理时间。已经退出则释放句柄；仍残留时，只在输入窗口已销毁或停止响应、且隔离目录没有实际视图时，结束固定句柄对应的旧进程。消息超时探测不在 UI 线程执行。
4. 最终使用检查和回收共用网页生命周期锁，防止与重新打开分组竞争。若分组重新使用，保守地延后检查；有下载任务的视图仍保留至任务结束后再进入关闭流程。

这覆盖正常关闭后的退出卡住，不是对任意活动网页的强制内存限制。后台网页仍沿用一小时未激活后休眠的策略，调试中的网页暂缓休眠。持久化资料保留，但不能把 Cookie/localStorage 回归推断为任意网站未保存表单或会话级数据的恢复保证。

使用 `SIA_CLOSE_FIRST=1 node scripts/test-browser-close-during-create.cjs [EXE路径]` 验证先关闭、恢复失败页面、切离及恢复窗口，并检查 Windows 心跳、同步 IPC、旧网站挂起请求确实断开，以及重新进入原隔离空间。设置 `SIA_CLOSE_MINIMIZE=0` 可排除窗口切换变量。脚本只恢复自己的隔离测试窗口；超时保存等待链（仅进程名与线程编号），可显式指定本地采样器记录线程栈。旧版第一轮超时，修复版连续六轮通过；默认创建期间关闭的六轮回归同样通过。

增加 `SIA_CHECK_PROFILE_RELEASE=1` 可验证回收：保留同组另一网页、保留关闭页签上的下载、在宽限期内重新使用同一隔离目录；随后关闭所有测试视图，持续探测原生 IPC，确认这些隔离目录的内核及子进程归零。重新进入已回收的目录后验证持久化 Cookie 和 localStorage，再次关闭并确认进程归零。统计脚本只匹配显式指定的独立测试目录及测试分组前缀，Windows PowerShell 脚本保存为带 BOM 的 UTF-8，避免中文注释被按系统代码页误解析。

资源回归已在真实发布 EXE 上通过：六轮关闭/切离窗口保持响应，两次回收检查均为零个测试分组进程（包括子进程）；同组剩余页和重新使用的页可继续切换，后台下载文件逐字节一致，持久化 Cookie/localStorage 可读回。默认创建期间关闭六轮、冷启动/恢复启动及 34 项 Rust 测试也通过。尚未覆盖所有第三方网站、扩展或长时间真实会话。

### 创建期间同步关闭的死锁

实际挂起进程的主线程调用栈显示：`wry::webview2::InnerWebView::new_in_hwnd` 正在创建相邻网页，初始化消息泵重入壳层 IPC；同步的 `close_browser_tab` 随即调用 `Webview::close`，在 `tauri_runtime_wry::WebviewWrapper::drop` 中等待外层创建流程持有的 WebContext 互斥锁。不同页签使用独立 WebView，并不意味着其创建和销毁没有共享主线程及上下文锁。

关闭命令改为异步任务，与网页初始化及扩展变更共用异步操作锁，等待期间不阻塞窗口消息。已有锁内的跨隔离范围重建调用内部关闭函数，避免重复加锁；下载结束后的隐藏网页清理也异步等待相同操作锁，不再在主线程回调内直接销毁。

运行 `node scripts/test-browser-close-during-create.cjs [EXE路径]`，通过 `NODE_PATH` 提供 Playwright。脚本启动真实 EXE 和新建的 D 盘诊断资料目录，用本地 HTTP 服务挂起旧网页请求，在新隔离环境创建期间从壳层 IPC 关闭旧网页，再验证旧视图已移除、新视图可切换、原生线程可响应。旧版第一轮超过 15 秒仍未返回；修复版连续六轮通过。测试只结束自己创建的进程树，不操作用户安装版实例。此回归覆盖创建/销毁重入，不代表所有网站的长期稳定性验证。

## 键盘与焦点消息重入（2026-10-23）

2026-10-23 对实际未响应的安装版进行只读采样：`WM_NULL` 在 1500ms 内没有响应，主线程阻塞在 `parking_lot::RawMutex::lock_slow`。外层 `KeyEventBuilder::process_message` 调用 `PeekMessageW` 时重入 `public_window_callback`，内层键盘回调再次等待同一把不可重入锁。

安装版没有对应的旧 PDB，诊断通过旧 EXE 与本地带 PDB 的 EXE 匹配多个连续机器码片段定位函数，并与原始调用栈核对。与 [Tao #1379](https://github.com/tauri-apps/tao/issues/1379) 的死锁路径一致；不能据此推断用户当时具体进行了哪一种焦点切换。

Tao 0.35.3 的键盘构建器在持有全局输入锁时查询消息队列，Windows 可能在查询期间派发其他线程发送的焦点消息，从而使主线程等待自己。系统焦点变化也可能在用户没有操作浏览器时发生。后台标签的自动休眠不是本次调用栈指向的阻塞路径。

## 修复依赖

浏览器使用 Tauri 2.12 系列及其 Tao 0.37 系列输入实现，同时将显式使用的 WebView2 COM、Windows 类型升级为与 Tauri 一致的版本。参考 [上游升级说明](https://github.com/tauri-apps/tao/issues/1349)。不修改 Cargo 缓存源码，不通过丢弃键盘消息规避问题。

## 回归方式

运行 `pnpm --filter @sia-ui/browser test:input-reentrancy`。测试在独立隐藏窗口中交错派发按下、字符、释放及跨线程焦点消息，并持续检查窗口心跳和键盘事件交付；不打开网页，不访问浏览器数据。脚本先校验夹具与浏览器锁文件中的 Tao 版本相同。

默认运行 10 秒；可设置 `SIA_INPUT_CHECK_SECONDS=60` 延长压力测试。原版 Tao 0.35.3 在相同夹具中 1.82 秒后因连续三次心跳超时而失败。

本次验证：旧版连续两次失败（1.82 秒、1.83 秒）；Tao 0.37.1 的 10 秒测试交付 27,276 个键盘事件，60 秒测试交付 155,632 个键盘事件，均保持响应。该压力测试覆盖已定位的输入重入死锁，不等价于所有网站和长期运行场景的稳定性保证。

`scripts/inspect-browser-hang.ps1 -BrowserProcessId <PID>` 可检查实际进程的响应和等待链，窗口超时返回退出码 1。诊断不结束用户进程，也不输出锁名称或网页内容。

## 安装后恢复会话时未响应

同日升级后的安装版又在启动时未响应。匹配安装 EXE 的 SHA-256 与本地 PDB 后，主线程调用栈定位到另一条重入路径：主 WebView2 初始化消息泵派发前端 IPC，`open_floating_tab_panel` 同步调用 `Window::add_child`，重新进入 `tauri_runtime_wry::create_webview`，等待外层尚未释放的 `web_context` 互斥锁。在主线程调用 `run_on_main_thread` 会直接执行，无法作为这里的延迟屏障。

修复在 Builder 中注册异步就绪状态，`setup` 完成覆盖层、标签面板和菜单预加载后发布结果。主入口等待 `wait_browser_ready` 才挂载 React；创建标签面板、网页的命令也等待就绪。失败结果展示为框架 Alert，避免无说明地停留在连接占位。等待通过 Tokio watch 挂起任务，不阻塞原生消息线程，不依赖固定延时。

`pnpm --filter @sia-ui/browser test:startup` 启动真实发布 EXE，首次使用新目录，保存仅包含本地测试网站的会话后再次启动，并检查工具栏、标签面板、真实网页恢复和连续原生 IPC 响应。修复前测试在恢复会话时因标签面板/原生线程超时失败。测试通过 `--diagnostic-data-dir` 隔离应用和 WebView2 目录，仅接受新目录或带测试标记的目录；只结束自身创建的进程树，不接触用户会话。诊断参数不改变正常安装版的数据路径。

修复后，完整启动脚本连续两轮通过（共四次实际 EXE 启动）。最后一轮同时检查显示后的 Windows 消息心跳；每次启动额外执行 20 次持续原生 IPC 检查。恢复网页由本地 HTTP 请求和页签标题回传共同确认，因为隔离小分组的 WebView2 环境不一定与主壳层共用调试端口。键盘压力测试再次通过（10 秒、31,170 个事件），Rust 的 17 项测试和公开 API 注释检查通过。以上使用独立测试资料，不代表已经验证用户原始资料下所有网站及扩展的长期行为。
